## What changed

Adds one function, `public.search_listings_nearby(...)` — additive, forward-only.
No table/column/enum/RLS changes.

SCR-001 created `listings.location` (generated `geography(Point,4326)`) and the GiST
index `listings_location_gix`, but nothing ever used them: radius search was a lat/lng
bounding box filtered to the exact circle **in the client, after pagination** — giving
wrong result counts (a box is ~27% larger than its inscribed circle), incomplete/irregular
pages, and per-page-only distance ordering (mobile TASK-022).

The RPC does the geo filter + distance ordering in Postgres:
- `st_dwithin(location, point, radius_m)` for the radius filter (GiST-indexable).
- `order by location <-> point` — KNN distance ordering (index-assisted).
- All scalar filters (status, type, category, condition, neighborhood, owner, price
  range, text) live in the function, so the client adds only `.select()`/`.range()` —
  no outer WHERE/ORDER, which keeps the function's distance order intact through
  pagination.

Returns `setof public.listings` so PostgREST still embeds `listing_photos` / owner /
category via the mobile client's existing `LISTING_SELECT`.

## Security / privacy

`security invoker` — existing RLS on `listings` applies unchanged (anon sees only
ACTIVE rows; owners see their own). The function returns exactly the columns a direct
table select already returns today (`lat`/`lng` were already in `LISTING_SELECT`), so it
introduces **no new coordinate exposure**. `grant execute` to `anon, authenticated`.

GiST index wins once rows accumulate). The predicate + index are in place; no further
action needed.
