# SCR-029 — Pre-publish listing moderation gate: `PENDING_REVIEW`

Status: Accepted
Date: 2026-09-01
Author: Codex
DB reviewer: Web lead
Migrations:

- `supabase/migrations/20260901130100_scr029_listing_status_transition_guard.sql`

## What changes

- Adds `PENDING_REVIEW` to the existing `public.listing_status` enum (`DRAFT`,
  `ACTIVE`, `PAUSED`, `SOLD`, `ARCHIVED`), inserted right after `DRAFT`. Plain
  `ALTER TYPE ... ADD VALUE`, its own migration file/transaction (Postgres
  forbids using a value added by `ADD VALUE` in the same transaction that
  added it).
- No RLS policy change. `listings_select_active` already restricts public
  (`anon`/`authenticated`) reads to `status = 'ACTIVE'`; `listings_select_own`
  already lets an owner see their own row regardless of status. A
  `PENDING_REVIEW` listing is therefore invisible to the public and visible
  only to its owner and staff by construction — no new policy needed.
- No trigger, no new table. `ListingsRepository.setStatus` (audited via
  `AuditRepository`/SCR-004) already handles arbitrary status transitions
  generically; `PENDING_REVIEW` is just added to the allowed-status list in
  application code (`LISTING_STATUSES` in `src/lib/repositories/listings.ts`,
  `ALLOWED` in `src/app/api/admin/listings/[id]/status/route.ts`, the
  `ListingStatus` union in `src/lib/api.ts`).

- **Second migration — `guard_listing_status_transition` trigger.** Grilling
  this surfaced a real gap: `listings_update_own` RLS (SCR-001) lets an owner
  `UPDATE` any column on their own listing, including `status`, with no
  restriction on the value, and `listingsApi.update()` in fethi-mobile already
  passes `status` straight through. Without a guard, an owner could call that
  same client API directly to set `status: 'ACTIVE'` on their own
  `DRAFT`/`PENDING_REVIEW` listing and self-publish, bypassing staff approval
  entirely — RLS alone does not enforce this gate. A `before update of status`
  trigger on `listings` now rejects `status → 'ACTIVE'` out of
  `DRAFT`/`PENDING_REVIEW` unless the caller is `service_role`
  (`auth.role()`, the same JWT-role signal PostgREST/RLS already relies on) —
  i.e. only the staff-gated admin route handler (service-role client) can
  perform that transition. Scoped to `UPDATE` only, not `INSERT`: a
  first-time insert setting `status: 'ACTIVE'` is untouched, since
  fethi-mobile's `sell/review.tsx` still does exactly that today and hasn't
  shipped its own switch to `PENDING_REVIEW` yet — blocking `INSERT` here
  would break current production listing creation before the mobile PR ships.
  Verified fethi-mobile has exactly one `listingsApi.update()` call site
  (`my-listings/[id]/edit.tsx`, category-only, never touches `status`), so
  this closes a latent hole with zero behavior change for current traffic.

Additive, forward-only. No existing table/column/row is touched; both
migrations are a no-op for every listing that already exists.

## Why

fethi-mobile issue #68 ("Feedback admin"): founder asked whether listings are
validated in admin before publishing. They are not — `sell/review.tsx` →
`listingsApi.create` in fethi-mobile defaults a new listing straight to
`ACTIVE`, which RLS makes immediately public. There is no gate today; the
existing admin "moderation queue" (WEB-010/WEB-011) is a reactive takedown
queue (DRAFT/PAUSED/ARCHIVED), not a pre-publish approval step. Board task:
**WEB-023**.

`DRAFT` is deliberately not reused for "awaiting review": `DRAFT` keeps
meaning "incomplete, never submitted" (a seller mid-flow), while
`PENDING_REVIEW` means "submitted, awaiting staff decision." Conflating the
two would confuse both seller-facing copy and the admin queue.

## RLS intent

No new policy. Existing `listings` RLS (SCR-001) already covers every case:

- `listings_select_active` (`anon`, `authenticated`): `status = 'ACTIVE'`
  only — `PENDING_REVIEW` rows are excluded, same as `DRAFT`/`PAUSED`/`ARCHIVED`
  today.
- `listings_select_own`: owner sees their own row at any status, including
  `PENDING_REVIEW` — a seller can see their listing is "submitted" rather than
  it silently vanishing.
- All `update`/`insert` on `listings` remain owner-or-service-role as today;
  staff approval writes go through the service-role admin route handler
  (`gateStaff('moderator')`), not client RLS. **Additionally enforced by the
  `guard_listing_status_transition` trigger** (see "What changes"): RLS's
  ownership check alone would let an owner set `status: 'ACTIVE'` on their
  own row via the existing client `update()` API, so the actual "only staff
  can approve" guarantee is a trigger, not a policy.

None.

## Affected consumers

- Web: **WEB-023** — extends the existing moderation queue
  (`src/app/(admin)/(authed)/listings/moderation/`) and the previously
  read-only `src/app/(admin)/(authed)/listings/pending/` page (which today
  incorrectly reads `status: DRAFT` — becomes the `PENDING_REVIEW` approval
  view with Approve/Reject actions) to surface and action `PENDING_REVIEW`
  listings. A sidebar badge (existing, previously-unused `badge` field on nav
  items) shows the live pending count so staff don't have to remember to
  check the queue.
- Mobile: **not built in this task.** `fethi-mobile`'s `sell/review.tsx` (via
  `listingsApi.create` in `fethi-mobile/src/shared/lib/api.ts`, which
  currently defaults `status` to `ACTIVE`) must change its default to
  `PENDING_REVIEW`, plus seller-facing copy explaining the listing is under
  review. Tracked in `docs/MOBILE-SYNC-NOTES.md` as a follow-up mobile task
  against `ProgixDev/fethi-mobile#68`. **Until that mobile PR ships, this
  migration is dormant** — no listing will actually reach `PENDING_REVIEW`,
  so there is zero behavior change for current production traffic.

## Rollback / compatibility

Postgres cannot remove an enum value once added (`DROP VALUE` doesn't exist).
If this gate is reverted, the safe rollback is application-level: stop
routing new listings into `PENDING_REVIEW` (mobile reverts its default to
`ACTIVE`, or is simply never shipped) and, if any rows are stuck in
`PENDING_REVIEW`, a one-off admin bulk-transition to `ACTIVE`/`ARCHIVED`. The
unused enum value staying in the type forever is cosmetic, not a compat
hazard — every other consumer treats `listing_status` as an open set already
(`LISTING_STATUSES` arrays are explicit allowlists, not `switch` statements
that would break on an unhandled case... except the `Record<ListingStatus,_>`
UI maps, which TypeScript forces to be updated for every value, so those are
safe by construction too).
