# SCR-013 — Fix `confirm_order_pickup` enum cast (SCR-012 B3 bugfix)

Status: Accepted
Date: 2026-07-12
Author: Dev A (shared backend lane)
Migration: supabase/migrations/20260712160000_scr013_confirm_pickup_enum_cast.sql

## What changed

`create or replace` of `public.confirm_order_pickup` (from SCR-012). Same
signature and return type — **no type regeneration**, additive/forward-only.

The SCR-012 version built `status` from a `CASE` whose branches were `text`
literals (`'COMPLETED'` / `'HANDOFF_PENDING'`). `orders.status` is the
`order_status` enum, and **assignment does not implicitly cast `text` → enum**
(only comparisons like the `status in (...)` guard do), so a successful pickup
confirmation failed at runtime with:

```
column "status" is of type order_status but expression is of type text
```

The SCR-012 verification only exercised the RPC's EXECUTE permission (denied for
`authenticated`) and the A1 payment gate throws before reaching the RPC, so the
successful-UPDATE path wasn't hit until the WEB-017 confirm-flow test. Fix: cast
both branches to `::public.order_status`.

## Verification (live)

Paid order, two parties:
- buyer confirms → `HANDOFF_PENDING` (buyer_confirmed=t, seller_confirmed=f)
- seller confirms → `COMPLETED` (both flags set, `completed_at` set)

EXECUTE remains `service_role`-only.
