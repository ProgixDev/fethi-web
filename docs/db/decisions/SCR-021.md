## What changes

One new Edge Function, no migration:

- **`didit-session-create`**: `POST { callback?, callbackMethod?, language? }`
  (user JWT), returns `{ url, sessionId, status }`. Calls Didit's
  `POST /v3/session/` (`https://verification.didit.me`) with
  `vendor_data: <profiles.id>`, using `DIDIT_API_KEY` + a new
  `DIDIT_WORKFLOW_ID` secret (a workflow UUID from the Didit dashboard —
  **not yet supplied**, function 503s `didit_unconfigured` until it is).

**Second writer to `profiles.kyc_session_id`**: SCR-020 introduced this
column, written by `didit-webhook` on `Approved`. This function is now a
second, best-effort writer — it records the session id immediately on
creation (before any webhook has fired), purely for staff visibility into an
abandoned/never-started session. `didit-webhook` remains the sole writer of
`kyc_status` itself; this function never touches that column. No RLS change
needed — `profiles`' existing owner-write policy (SCR-001) already covers a
service-role update performed on the caller's own behalf.

## Why

Issue #28 requires "verification sessions are created only for the
authenticated user through the backend" and "mobile clients never receive
the Didit API secret." This function is that backend boundary — the mobile
app gets back only a hosted `url` to open, never `DIDIT_API_KEY`.

Idempotency is Didit's own, not reimplemented here: per their docs, a
`vendor_data` with an unfinished session already open returns that existing
session (still `201`) rather than creating a duplicate. So this function
does no dedup of its own — it always calls Didit and trusts that contract.

## RLS intent

No RLS change. Reuses `profiles`' existing owner-scoped write policy
(SCR-001) via the service-role client, exactly like `didit-webhook`'s
`kyc_status`/`kyc_decision` writes (SCR-020) and every other transactional
Edge Function in this repo (`orders-create`, `offers-respond`, etc.).
