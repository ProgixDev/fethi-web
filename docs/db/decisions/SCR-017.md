## What changes

One additive, forward-only change:

- **New table `public.waitlist`**: `id uuid pk`, `email text not null`,
  `referral_code text` (nullable), `source text not null default 'homepage'`,
  `created_at timestamptz not null default now()`.
- **Unique index** on `lower(email)` — one row per email, database-enforced.
- RLS enabled, **no policies added**. See "RLS intent" below.

No existing table, column, enum, or policy is touched.

## Why

`POST /api/marketing/waitlist` (`src/app/api/marketing/waitlist/route.ts`) has
shipped since WEB-015 with a documented `TODO(SCR)`: it validates the email,
runs spam/self-referral guards, dedupes, and returns a success response —
but never writes anywhere. The "dedupe" is an in-process `Set` that resets on
every redeploy or cold serverless start. On Vercel this means: every signup
today is silently discarded, and even the in-memory dedupe is close to
meaningless given how often serverless instances cycle. This is the only
conversion action on a pre-launch marketing site.

## RLS intent

No client policies. Unlike `categories` (public reference data meant to be
read by every visitor) or `listings` (owner-scoped read/write), a waitlist
signup has no legitimate case for a browser to read or write it directly:

- **No anon SELECT** — nothing in the product reads waitlist rows from the
  browser (no "you're #412 in line" feature exists), and email addresses are
  PII with no reason to be client-fetchable.
- **No anon INSERT** — this is the one worth stating explicitly, because
  "public insert" was the phrase in the original `TODO(SCR)` comment. An
  RLS policy allowing `anon` to `insert` would let anyone holding the public
  publishable key (which is, by definition, embedded in client JS) write
  directly to Supabase's REST API — bypassing the route handler's email
  format check, spam guards, and self-referral logic entirely. That's a
  direct spam vector for a public marketing table with no auth gate.
- **Sole writer**: the route handler, server-side only, via the
  service-role client (`src/lib/supabase/admin.ts`, already used the same
  way by every staff-gated admin route — the difference here is this route
  itself has no staff/user auth, since anonymous visitors are the intended
  callers, but the *write* still only ever happens inside trusted server
  code, never from the browser). Service-role bypasses RLS regardless of
  what policies exist, so "no policies" is sufction for a locked table.

If a future feature needs a staff admin screen to browse waitlist entries,
that's a small additive change (a repository + staff-gated route, same
pattern as every other admin domain) — not part of this SCR.

## Edge Function (if any)

None. Plain table write through the service-role Supabase client inside the
existing Next.js Route Handler.

## Affected consumers

- Mobile: **none.** This table backs a web-only, pre-launch marketing
  surface (the waitlist form on the marketing site); nothing in
  `fethi-mobile` reads or writes it. Per `docs/db/COORDINATION.md`, the
  vendored-types/mobile-sync steps below are still followed for the
  contract file itself (types must stay in sync so mobile's `tsc` doesn't
  drift), but no mobile task is unblocked or affected by this change, so the
  cross-repo copy into `fethi-mobile/src/shared/types/` is not performed as
  part of this SCR — there is nothing there to consume it, and copying an
  unused type addition is pure churn. Flagging this explicitly rather than
  silently skipping it, per the precedent set in SCR-016 for the
  `docs/db/CONTRACT.md` checklist item.
- Web: `src/app/api/marketing/waitlist/route.ts` (this SCR's actual
  reason for existing).

## Rollback / compatibility

Purely additive — a new table nothing else references (no FK from any
existing table into `waitlist`, no FK from `waitlist` into anything). Safe
to apply at any time; if it needs to be reverted, `drop table
public.waitlist` in a later migration undoes it cleanly with no cascading
impact, since nothing else in the schema depends on it existing.

## Evidence

Docker (needed for `supabase start` / local stack) was unavailable in this
session, so this wasn't exercised against a local instance first — instead,
verified directly against the applied remote migration via
`supabase db query --linked`:

| Step | Query | Result |
| --- | --- | --- |
| 1 | `insert into public.waitlist (email, source) values ('smoketest@example.com', 'homepage') returning ...` | Succeeds, row returned with generated `id`/`created_at` |
| 2 | `insert into public.waitlist (email, source) values ('SMOKETEST@example.com', 'footer')` | Fails: `23505 duplicate key value violates unique constraint "waitlist_email_key" DETAIL: Key (lower(email))=(smoketest@example.com) already exists.` — confirms the case-insensitive unique index works exactly as the route handler's `23505` catch expects |
| 3 | `delete from public.waitlist where email = 'smoketest@example.com'` | Cleans up the test row; `select count(*)` confirms `0` |

Not separately re-verified: RLS lockout for `anon`/`authenticated` (no policy
exists, so this is enforced by absence rather than a predicate to test —
lower risk than a mis-written policy, but also nothing to positively assert
beyond "table has RLS enabled and zero policies," which `\d+ public.waitlist`
or the generated types already confirm structurally).
