## What changes

Additive, forward-only. One new table to record every staff/admin write action
(user suspend/ban/reactivate in WEB-009; listing pause/archive/soft-hide/restore
in WEB-010), so moderation is auditable as both tasks require.

- Table `staff_audit_log`:
  - `id uuid PK default gen_random_uuid()`
  - `actor_id uuid not null references auth.users(id) on delete restrict`
    (the staff member who performed the action)
  - `action text not null` (e.g. `user.suspend`, `user.ban`, `user.reactivate`,
    `listing.pause`, `listing.archive`, `listing.restore`)
  - `target_type text not null` (`user` | `listing`)
  - `target_id uuid not null` (the affected profile/listing id)
  - `before jsonb` / `after jsonb` (status snapshot for reversibility)
  - `reason text`
  - `created_at timestamptz not null default now()`
  - indexes on `(target_type, target_id)` and `(created_at desc)`.

No enums added (action/target are free text, kept additive — future actions need
no migration). No columns added to `profiles`/`listings`; the existing
`user_status` and `listing_status` enums already cover suspend/ban/pause/archive.

Also adds supporting btree indexes for the admin list/sort paths (additive, no
type/contract impact): `profiles(status)`, `profiles(kyc_status)`,
`profiles(created_at desc)`, `listings(status, created_at desc)`,
`listings(created_at desc)` — the admin screens filter by status/kyc/neighborhood
and sort by created_at via the service-role client.

## Why

WEB-009 and WEB-010 acceptance criteria require staff actions to be **audited**.
There is no audit table in SCR-001/002/003. Rather than add columns ad-hoc, this
SCR introduces a single, reusable audit table for all admin moderation lanes
(WEB-009..014). Board: WEB-009, WEB-010; reused by WEB-011..013.

## RLS intent

- `staff_audit_log`: RLS **enabled, NO policy for anon/authenticated** → the table
  is invisible to the browser. All reads and writes go through the **service-role
  client inside admin Route Handlers**, which bypasses RLS and is gated by
  `requireStaff()` + `hasRole(...)` in application code. Mobile never touches it.

## Edge Function (if any)

None. Written from the admin Next.js Route Handlers (service-role client) that
perform the moderation mutation, in the same transactional path.

## Affected consumers

- Web: WEB-009 (user suspend/ban/reactivate), WEB-010 (listing moderation),
  reused by WEB-011 (reports), WEB-012 (KYC), WEB-013 (disputes/refunds).
- Mobile: **none** — staff-only, service-role-gated, invisible via RLS. Types
  still vendor to mobile for contract completeness.
