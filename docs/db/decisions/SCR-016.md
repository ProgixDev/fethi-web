## What changes

One additive, forward-only change:

- **`listings.meeting_venue text`** (nullable, no default). Holds the free-text
  public meetup spot the seller enters (e.g. `"Café X, République"`) when they
  choose a public handoff for the listing. No new table, no new enum, no RLS
  policy change (see RLS intent below), no index — this column is not currently
  queried/filtered on, only stored and displayed.

No other column is added in this SCR. See "Scope decision" below for why
`pickup_method` and `availability` are explicitly out of scope here.

## Why

Issue #23 ("Collect the selected public handoff venue") is fully built
client-side on `fethi-mobile` branch `fix/issue-23-public-venue` (commit
`78d61f6`): the sell flow's `/sell/pickup` step requires a venue name when
"Lieu public" is selected, the value survives draft save/resume (client-only,
`AsyncStorage`), the review/edit screens display it, and publish is blocked
with a validation message if it's missing. All of that already meets the
issue's acceptance criteria without any backend change.

The one criterion that does need a backend change: **"Venue is included in
the published listing."** Today it isn't — `CreateListingRequest.meetingVenue`
is accepted by the `api.ts` contract and populated by the review screen
(`src/app/sell/review.tsx`) whenever `pickupMethod === 'meeting'`, but
`listingReqToColumns` in `src/shared/lib/api.ts` deliberately does not map it
to a DB column, because `listings` doesn't have one — the value is silently
dropped before the Supabase insert. This SCR adds that column so the mapping
can be wired up for real.

## Scope decision: `meeting_venue` only, not `pickup_method`/`availability`

The investigation that led to this SCR flagged a fair concern: a bare
`meeting_venue` column with no `pickup_method` column is semantically
underspecified in the abstract — the server has no explicit way to know a
stored venue string means "this was a public handoff" versus something else,
since pickup method itself isn't persisted anywhere either.

In the abstract, yes. In this codebase, no, for two concrete reasons:

1. **The client already gates the value on the choice.** Look at
   `src/app/sell/review.tsx`:
   ```ts
   meetingVenue:
     draft.pickupMethod === 'meeting' ? draft.meetingVenue.trim() : undefined,
   ```
   `meetingVenue` is only ever sent — and therefore only ever written to the
   new column — when the seller picked the public-meetup option. A non-null
   `listings.meeting_venue` is already, by construction of the one and only
   code path that writes it, implicit proof the listing is a public handoff.
   There is no other writer. A future SQL query or admin view that wants "is
   this a public handoff?" can use `meeting_venue is not null` and it will be
   correct for as long as this is the only writer — which is exactly why this
   SCR calls that out explicitly, so a future reader doesn't have to
   rediscover it.

2. **`pickup_method` and `availability` are not part of the actual gap.**
   `CreateListingRequest` (the `api.ts` contract) does not even include
   `pickupMethod` or `availability` fields — only `meetingVenue` is sent to
   the backend today (`draft.pickupMethod` and `draft.availability` are pure
   client/`SellDraft` state, never serialized into the publish payload). Issue
   #23's acceptance criteria are specifically about the venue field. Adding
   `pickup_method` (and, to make it meaningful, presumably `availability` too)
   would mean inventing and shipping a materially bigger contract change —
   new enum, new request fields, new UI wiring to actually send them, new
   read-side consumption — that nothing in this issue asked for and that
   isn't "clearly low-risk and clearly required" (the bar this SCR is held
   to). That's a legitimate follow-up (worth its own issue/SCR if the product
   wants pickup method queryable — e.g. to filter "show me only public
   meetup listings" — but it is not this issue), not something to bundle into
   a single-column fix opportunistically.

Net: the narrower change is the correct one. It closes the exact gap issue
#23 identifies, matches what the client already sends, and doesn't grow the
contract surface speculatively. If a later feature needs `pickup_method` as
its own filterable/queryable column, that's a new SCR with its own
`Affected consumers` and its own migration of the *sending* side, not a
retroactive justification bolted onto this one.

## RLS intent

No RLS policy changes. `listings` RLS is **row-level**, not column-level
(`listings_select_active`, `listings_select_own`,
`listings_insert_own`, `listings_update_own`, `listings_delete_own` from
SCR-001) — a new nullable column on an existing table is automatically
covered by whatever row a policy already permits/denies:

- `anon`/`authenticated` (non-owner): can `select` the row (and therefore
  `meeting_venue`) only when `status = 'ACTIVE'`, same as every other column
  — public listings' venue is meant to be publicly visible (that's the whole
  point: a buyer needs to know where to meet), so this is the intended
  behavior, not a leak.
- `authenticated` as owner: full `select`/`insert`/`update`/`delete` on their
  own rows, same as every other column — can write `meeting_venue` on their
  own listing (draft or published), matching how every other listing field
  behaves today.
- No new predicate is needed and none is added. Verified locally (see
  Evidence) that inserting/reading a `meeting_venue` value round-trips
  through the existing policies exactly like `neighborhood` or any other
  plain nullable text column already on the table.

## Edge Function (if any)

None. This is a plain column read/written directly through PostgREST behind
the existing `listingsApi.create`/`update` in `fethi-mobile/src/shared/lib/api.ts`,
same as the rest of `listings`.

## Rollback / compatibility

Purely additive — a new nullable column with no default and no constraint.
Existing rows get `NULL`, which is a valid, expected value (any listing that
isn't a public handoff). No existing reader breaks: nothing selected `*` in a
way that would choke on an extra column, and no code anywhere assumed the
`listings` row shape was closed. If this needs to be reverted, drop the
column in a later migration — nothing else depends on it existing gone
that a rollback would need to unwind (no FK, no trigger, no generated
column derived from it).
