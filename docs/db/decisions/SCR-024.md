## What changes

- Add authenticated Edge Function `orders-price-quote` with the same pricing
  inputs as `orders-create`.
- Move all pricing arithmetic into `_shared/pricing.ts`, consumed by both
  functions.
- Reconcile the approved fee model across VENTE, LOCATION, SERVICE, and
  accepted offers:
  - buyer fee: zero;
  - added tax/VAT: zero;
  - buyer total: advertised/agreed item price;
  - seller commission: 5%, rounded to the nearest cent;
  - seller net: item price minus seller commission.
- Card orders persist the seller commission in `orders.fee_cents`; no-card
  handoff orders keep `fee_cents = 0` because nothing is collected at order
  time and instead book the same commission in `seller_fee_receivables`.
- Every Order snapshots item, buyer fee, tax, seller fee, payment method, and
  pricing version so later receipts never reconstruct historical money rules.

## Why

The old client displayed a buyer-side 5% fee (with a €0.95 sale minimum), while
seller publishing screens and handoff receivables also applied a separate 5%
seller deduction. This could turn a €10 listing into €10.95 for the buyer while
also reducing seller proceeds, contradicting issue #30's transparency goal and
the approved seller-side business model.

Checkout must preview the exact server calculation before confirmation; copying
the formula into mobile is not authoritative and can drift from order creation.

## RLS intent

No RLS change. Both functions authenticate the caller. They use service role
only after resolving the JWT user and never accept a client-supplied total.
Offer quotes validate that the accepted offer belongs to the caller and listing.

## Edge Function contracts

### `POST orders-price-quote`

Input:

```json
{
  "listingId": "uuid",
  "offerId": "uuid?",
  "rentalStart": "YYYY-MM-DD?",
  "rentalEnd": "YYYY-MM-DD?",
  "serviceHours": 1,
  "paymentMethod": "card | handoff"
}
```

Output:

```json
{
  "pricingVersion": "seller-commission-v1",
  "pricingFingerprint": "seller-commission-v1:eur:<listing-id>:direct:1000:0:0:1000:50:950:50:0::",
  "currency": "eur",
  "itemCents": 1000,
  "buyerFeeCents": 0,
  "taxCents": 0,
  "buyerTotalCents": 1000,
  "sellerFeeCents": 50,
  "sellerNetCents": 950,
  "depositCents": 0,
  "rentalStart": null,
  "rentalEnd": null
}
```

`persistedOrderFeeCents` is also returned for contract verification: 5% for
card, zero for handoff. Mobile does not use it for display.

Mobile passes `pricingFingerprint` back to `orders-create`. The function still
recomputes all monetary values from server data and uses the fingerprint only
to reject a stale confirmation with `pricing_changed`; it is never trusted as
a client-supplied total.

### `POST orders-create`

Input and top-level order response remain compatible. Monetary semantics are
corrected: `amountCents` is the buyer total/item price and `feeCents` is the
seller commission actually withheld from a card order.

## Affected consumers

- Mobile issue #30 checkout screens and receipts.
- `payments-create-intent`: existing destination-charge application fee now
  deducts the approved seller commission instead of a buyer surcharge.
- `stripe-webhook`: refuses a successful PaymentIntent whose amount, currency,
  application fee, Order id, or PaymentIntent id does not match the Order.
- Issues #35 and #37: held proceeds and accepted offers consume the same quote.

## Refund policy

The approved full pre-validation refund behavior is already implemented by the
admin refund path with both `reverse_transfer=true` and
`refund_application_fee=true`. Thus the buyer receives the full charged item
price, the seller transfer is reversed, and MyStreet returns its commission.

## Rollback / compatibility

The quote function is additive. Reverting `orders-create` would restore the old
buyer surcharge and must be paired with reverting the mobile checkout display;
the two must never be released independently.
