# SCR-028 — Support inbox: `support_tickets` + `support_ticket_messages`

Status: Accepted
Date: 2026-09-01
Author: Codex
DB reviewer: Web lead
Migrations:

- `supabase/migrations/20260901121500_scr028_support_ticket_mark_read.sql`

## What changes

- New enum `public.support_ticket_status` — `OPEN`, `IN_PROGRESS`, `RESOLVED`, `CLOSED`.
- New enum `public.support_sender_role` — `USER`, `STAFF`.
- New table `public.support_tickets`: `id`, `user_id` (→ `profiles`), `subject`,
  `status` (default `OPEN`), `assigned_staff_id` (→ `staff_members`, nullable),
  `last_message`, `last_message_at`, `last_sender_role`, `unread_by_user`,
  `unread_by_staff`, `created_at`, `updated_at`.
- New table `public.support_ticket_messages`: `id`, `ticket_id` (→
  `support_tickets`), `sender_id` (→ `profiles`), `sender_role`, `body`,
  `created_at`.
- Trigger `sync_ticket_on_message` (mirrors SCR-003's `sync_thread_on_message`):
  on new message, updates the parent ticket's `last_message*` fields, bumps the
  other party's unread counter, and reopens a `RESOLVED`/`CLOSED` ticket to
  `OPEN` when the **user** replies after staff closed it.
- Both tables added to the `supabase_realtime` publication (mobile needs live
  updates the same way `messages`/`threads` already do).
- Indexes: `support_tickets(user_id, updated_at desc)`,
  `support_tickets(status, updated_at desc)` (admin inbox queue),
  `support_ticket_messages(ticket_id, created_at)`.
- Follow-up function `mark_support_ticket_read(p_ticket_id uuid)` — `support_tickets`
  has no client `UPDATE` policy (staff-only), so — the same gap SCR-003/SCR-006
  hit for `threads` — the ticket owner needs a `SECURITY DEFINER` escape hatch,
  self-gated to `user_id = auth.uid()`, to clear their own `unread_by_user`.

Additive, forward-only. No existing table/column is touched.

## Why

fethi-mobile issue #77 ("Feedback admin"): founder called the support inbox
priority — users have no in-app way to message support, and admin has no way to
see or answer requests. Was tracked in the admin repo as `#77`, previously
deferred (see `/tmp/handoff-fethi-web-admin-feedback.md`) because it needed a
real table + backend, not a quick fix. Board task: **WEB-022**.

## RLS intent

- `support_tickets`
  - `select`: owner (`user_id = auth.uid()`) OR staff with `support` or `admin`
    role (`has_staff_role(auth.uid(), 'support') or has_staff_role(auth.uid(), 'admin')`).
  - `insert`: authenticated, `user_id = auth.uid()` (a user opens their own
    ticket; staff never creates a ticket on a user's behalf in this iteration).
  - `update`: staff only (status/assignment changes). The owner never updates a
    ticket row directly — replying goes through `support_ticket_messages`, whose
    trigger updates the parent row under `security definer`.
  - `delete`: none (service-role only, no policy).
- `support_ticket_messages`
  - `select`/`insert`: ticket owner OR staff (support/admin), gated through a
    `security definer` helper `public.is_support_ticket_participant` (mirrors
    `is_thread_participant`) to avoid recursive RLS on `support_tickets`.
  - `update`/`delete`: none — messages are append-only.

## Edge Function (if any)

None. Reads/writes go through RLS-gated PostgREST calls behind
`fethi-mobile/src/shared/lib/api.ts` and the admin's Supabase client, same as
`threads`/`messages`. No service-role secret needed.

## Rollback / compatibility

Both tables are new — nothing else reads or writes them yet, so this ships with
zero blast radius on existing features. If the support inbox is cut later, the
tables can simply stop being read; no other table has a foreign key into them.
