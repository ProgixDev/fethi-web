## What changes

Additive, forward-only. The second real schema — the transactional core. Adds:

**Enums** (native; values match the shipped mobile `api.ts` exactly — never rename,
only `ADD VALUE`):
- `offer_status` = PENDING | ACCEPTED | REJECTED | EXPIRED | WITHDRAWN  (mobile `OfferStatus`)
- `order_status` = AWAITING_PICKUP | HANDOFF_PENDING | COMPLETED | CANCELLED | REFUNDED | DISPUTED  (mobile `ApiOrderStatus`)
- `message_kind` = TEXT | PHOTO | LOCATION | OFFER | PICKUP | SYSTEM  (mobile `MessageKind`)

**Tables**:
- `threads` — one conversation per `(listing_id, buyer_id)`; `buyer_id` + `seller_id`
  (seller derived from the listing owner), `last_message`/`last_message_at`/`last_sender_id`
  + per-participant `buyer_unread`/`seller_unread` counters, timestamps. `unique
  (listing_id, buyer_id)` (open-or-retrieve), `check (buyer_id <> seller_id)`.
- `messages` — `thread_id`→threads, `sender_id`→profiles, `kind message_kind`, `text`,
  `image_url`, optional `metadata jsonb`, `created_at`. (mobile `ApiMessage`)
- `message_attachments` — `message_id`→messages, `storage_path`, `content_type`,
  `width`/`height`/`byte_size`. Backs `threadsApi.sendPhoto`.
- `offers` — `listing_id`/`buyer_id`/`seller_id`, `amount_cents`, `message`, `status
  offer_status` (default PENDING), `response_message`, `responded_at`, `expires_at`
  (default now()+48h), `order_id` (the order an accept produced). (mobile `OfferResponse`)
- `orders` — `buyer_id`/`seller_id`/`listing_id` (FK `on delete restrict` — an order
  is a financial record), a denormalised listing snapshot (`listing_title`/`listing_thumb`/
  `listing_type`), `amount_cents`/`fee_cents`/`deposit_cents`, `rental_start`/`rental_end`,
  `status order_status` (default AWAITING_PICKUP), `buyer_confirmed`/`seller_confirmed`,
  `deposit_released`, `cancelled_by`/`cancellation_reason`, `offer_id`, lifecycle
  timestamps. (mobile `ApiOrder`)
- `order_events` — immutable audit row per transition (`from_status`/`to_status`/`actor_id`/
  `note`/`metadata`).
- `idempotency_keys` — `PK (scope, key)`, `response jsonb`; backs the `Idempotency-Key`
  header so transition-fn retries never duplicate an order / double-apply.

**Indexes** (per the migration plan): `messages(thread_id, created_at)`;
`threads(listing_id)`, `threads(buyer_id, last_message_at desc)`,
`threads(seller_id, last_message_at desc)`; `offers(listing_id, buyer_id, status)`,
`offers(seller_id, status)`, partial-unique one live (PENDING) offer per buyer/listing;
`orders(buyer_id, created_at desc)`, `orders(seller_id, created_at desc)`,
`orders(status)`, `orders(listing_id)`; `order_events(order_id, created_at)`.

**Triggers**: `messages` insert → maintains `threads.last_message*` + increments the
OTHER party's unread counter (SECURITY DEFINER); `updated_at` touch triggers.

**Helper**: `is_thread_participant(thread_id, uid)` SECURITY DEFINER (search_path=public,
EXECUTE revoked from PUBLIC) — message/attachment RLS gates on thread membership via
this, avoiding recursive RLS + per-row `auth.uid()` cost (mirrors SCR-002 `is_staff`).

**Realtime**: `messages`, `threads`, `offers`, `orders` added to the
`supabase_realtime` publication. Mobile keeps subscriptions narrow by `thread_id`.

**Edge Functions** (Deno, `supabase/functions/`): `offers-respond`, `orders-create`,
`orders-transition` (see below). Authored; **deploy pending** (CLI needs Docker,
unavailable in this environment).

## Why

Unblocks the mobile transactional chain — **TASK-007** (messaging) and **TASK-010**
(offers/orders) — and the web admin order/dispute read models. Board: **WEB-005**.
Enum values, the buyer/seller split, the offer/order field shapes, and the message
kinds are dictated by the already-shipped mobile contract (`fethi-mobile/src/shared/lib/api.ts`);
this SCR makes the database match it.

## RLS intent

- `threads`: SELECT to the two participants only (`auth.uid() in (buyer_id, seller_id)`).
  INSERT by the buyer (`auth.uid() = buyer_id`), the named seller must own the listing.
  No client UPDATE — `last_message`/unread are trigger/service-role maintained.
- `messages`: SELECT/INSERT only for thread participants (via `is_thread_participant`);
  INSERT must be `sender_id = auth.uid()`. No client UPDATE/DELETE.
- `message_attachments`: SELECT for participants of the parent message's thread; INSERT
  only by the message author.
- `offers`: SELECT to buyer + seller. INSERT by the buyer as a PENDING offer on someone
  else's listing (seller must own the listing). **No client UPDATE/DELETE** — status
  transitions run service-role in `offers-respond`.
- `orders`: SELECT to buyer + seller. **No client write policy at all** — create and all
  transitions run service-role in `orders-create` / `orders-transition`. Raw clients can
  never mutate order state.
- `order_events`: SELECT to the order's parties; writes service-role only.
- `idempotency_keys`: RLS enabled, **no policy** → anon/authenticated see nothing; only
  the service role (RLS-bypassing) reads/writes it from the Edge Functions.

## Edge Function (if any)

All three take a **user JWT** (Authorization) to authenticate, perform invariant checks,
then mutate as **service role** (the only path that can write offers/orders status). All
honour an optional `Idempotency-Key` header backed by `public.idempotency_keys`. Secrets
are Edge secrets (`SUPABASE_URL`/`SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY`), never
`NEXT_PUBLIC`/`EXPO_PUBLIC`.

- `offers-respond` — `POST { offerId, action: accept|reject|withdraw, message? }`.
  accept/reject: seller only; withdraw: buyer only. Only PENDING transitions; an accept
  on an expired offer is rejected and the offer auto-marked EXPIRED. Guarded update
  (`...eq('status','PENDING')`) blocks double-accept. → mobile `offersApi.*`.
- `orders-create` — `POST { listingId, amountCentsOverride?, offerId? }`. Buyer can't buy
  own listing; if `offerId`, the offer must be ACCEPTED, this buyer's, on this listing, and
  not already ordered. Idempotency-Key dedups retries. Writes an `order_events` create row.
  → mobile `ordersApi.create`.
- `orders-transition` — `POST { orderId, action: confirm-pickup|cancel, reason? }`. Party-
  only. confirm-pickup: each side confirms; AWAITING_PICKUP→HANDOFF_PENDING→COMPLETED on the
  second confirmation. cancel: AWAITING_PICKUP/HANDOFF_PENDING→CANCELLED; rejected once
  terminal (COMPLETED/CANCELLED/REFUNDED). → mobile `ordersApi.confirmPickup`/`cancel`.

## Decisions (self-grilled; flagged for human ratification)

1. **No `thread_participants` join table.** The marketplace conversation is strictly 1:1
   (buyer ↔ listing owner). Two columns (`buyer_id`/`seller_id`) are clearer, give cheap
   `(buyer_id)`/`(seller_id)` indexes the migration plan asks for, and avoid a join on every
   RLS check. If group threads ever appear, a later SCR adds the join table additively.
2. **One thread per `(listing, buyer)`** (`unique`). Matches mobile `threadsApi.open` ("crée
   ou retrouve"). Re-opening returns the existing thread.
3. **Orders have NO client write policy; offers have no client UPDATE.** All state changes go
   through the Edge Functions as service role — the WEB-005 invariant "raw clients never
   mutate order/offer state." Reads stay client-side under RLS.
4. **Offer expiry default 48h** (`now() + interval '48 hours'`). The mobile `expiresAt` is a
   non-null string; a default keeps direct inserts valid. **Product question:** confirm 48h
   is the desired offer TTL (chosen default: 48h).
5. **`orders.fee_cents` default 0.** Marketplace fee computation is owned by WEB-006 (Stripe);
   SCR-003 stores the column so the mobile `feeCents` contract exists, defaulted to 0 until
   the fee policy lands. **Product question:** fee schedule (chosen default: 0 until WEB-006).
6. **`confirm-pickup` is two-sided** (buyer + seller each confirm) → COMPLETED only when both
   have, with an intermediate HANDOFF_PENDING. The mobile contract exposes
   `buyerConfirmed`/`sellerConfirmed` + both statuses, which this implements. **Product
   question:** confirm two-sided handoff vs. buyer-only confirmation (chosen default: two-sided).
7. **`REFUNDED`/`DISPUTED` are reachable only by service role** (WEB-006 refund webhook / WEB-008
   disputes), not by the SCR-003 transition fn — they exist in the enum for the contract.
8. **Listing FK on orders is `on delete restrict`** (vs. cascade on threads/offers): an order is a
   financial record and must survive a listing deletion. `cancelled_by`/`last_sender_id` use
   `on delete set null`.

## Rollback / compatibility

Forward-only, additive. Nothing in production depended on these tables (they did not exist).
Enum values may be added later but never renamed (mobile reads the exact tokens). The denormalised
order snapshot (`listing_title`/`thumb`/`type`) is captured at creation so an order survives later
listing edits/deletes. Realtime publication membership is additive. To change a transition rule,
add a new Edge Function version / a new SCR — never edit this merged migration.
