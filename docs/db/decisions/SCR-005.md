## What changes

Additive, forward-only. Backs the App Store / Google Play hard blockers driven by
**fethi-mobile TASK-014** (store-compliance). The mobile client seam for all of
this already ships (behind `src/shared/lib/api.ts`) against the contract below;
this SCR is what makes it real server-side. Web owns the DB, RLS and Edge
Functions — mobile must not author them (see `docs/WEB-BACKEND-SYNC.md`).

1. **Table `blocked_users`** — owner-scoped UGC blocking.
   - `id uuid PK default gen_random_uuid()`
   - `blocker_id uuid not null references auth.users(id) on delete cascade`
   - `blocked_id uuid not null references auth.users(id) on delete cascade`
   - `reason text`
   - `created_at timestamptz not null default now()`
   - unique `(blocker_id, blocked_id)`; index on `blocker_id`.
   - `check (blocker_id <> blocked_id)` (cannot block yourself).

2. **Table `reports`** — UGC reporting (coordinate with mobile TASK-013).
   - `id uuid PK`, `reporter_id uuid not null references auth.users(id)`,
     `target_type text not null` (`LISTING` | `USER` | `THREAD` | `MESSAGE`),
     `target_id uuid not null`, `reason text not null`, `details text`,
     `status text not null default 'OPEN'`
     (`OPEN` | `REVIEWING` | `ACTIONED` | `DISMISSED`),
     `created_at timestamptz not null default now()`.
   - rate-limit index on `(reporter_id, created_at desc)` (client expects a
     `RATE_LIMITED` error code — enforce in the Edge Function / a trigger).

3. **Edge Function `account-deletion`** — see signature below. Orchestrates
   server-side delete/anonymize because **a user's JWT is not invalidated
   instantly on delete**; the function runs service-role and re-checks account
   status, and sensitive RLS paths must gate on account status too.

4. **Edge Function `account-export`** — assembles the user's data (RGPD) and
   delivers it by email; returns an accusé only.

## Why

App Store Review **5.1.1(v)** (in-app account deletion) and Google Play
data-safety require an in-app deletion + data-export path; UGC apps require
report + block. fethi-mobile **TASK-014** builds the entire client surface
(deletion/export UI, block actions on listings/threads/profiles, `blocked_users`
content hiding) behind the api.ts seam. Without this SCR those calls hit nothing.

Cross-repo map (`docs/WEB-BACKEND-SYNC.md`) labels this **WEB-008**.

## RLS intent

- `blocked_users`: authenticated; `blocker_id = auth.uid()` for SELECT/INSERT/
  DELETE (you only ever see/create/remove **your own** block rows). No UPDATE.
- `reports`: authenticated INSERT where `reporter_id = auth.uid()`; **no** client
  SELECT (moderation is staff-only via service role / admin app). Rate-limit
  enforced server-side → surface `RATE_LIMITED`.
- Deletion/export are **service-role only** via Edge Functions — never a direct
  client table write.

## Edge Function (if any)

- `POST /me/deletion` (`account-deletion`) — user JWT in; verifies no active
  order / open dispute (else `409 { code: 'DELETION_BLOCKED' }`); deletes or
  anonymizes profile, listings, messages, offers, orders per retention policy;
  idempotent (re-call on a half-deleted account converges). Returns
  `{ status: 'DELETED' | 'SCHEDULED', scheduledFor? }`. Must also flip an account
  status that sensitive RLS/Edge paths check, so a still-valid JWT can't act on a
  deleted account.
- `POST /me/export` (`account-export`) — user JWT in; queues/sends the archive by
  email; returns `{ status: 'QUEUED' | 'SENT', deliveryEmail? }`.
- `POST /me/blocked`, `GET /me/blocked`, `DELETE /me/blocked/:userId` — may be a
  thin Edge layer or direct PostgREST against `blocked_users` under the RLS above
  (client seam `blockedApi` already targets these paths).
- `POST /reports` — already consumed by `reportsApi`; persist to `reports` with
  rate-limit.
- Secrets: service-role key + email provider key must be **Edge secrets**, never
  `EXPO_PUBLIC_*` / `NEXT_PUBLIC_*`.

## Affected consumers

- Mobile: **TASK-014** (deletion/export/legal/block/report surfaces — client
  shipped, gated on this SCR), **TASK-013** (reports backend — coordinate).
- Web: admin moderation queue reads `reports` (service role); user-management may
  read `blocked_users` for support.

## Rollback / compatibility

Fully additive — two new tables + two new Edge Functions. No existing column is
changed or dropped, so the web app already in production is unaffected. If rolled
back, the mobile client seam degrades gracefully (block list returns empty,
deletion/export calls surface a network error and no data is touched).
