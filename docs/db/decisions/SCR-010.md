## What changes

Additive, forward-only. Introduces the notification store (in-app feed) and the
server-side Expo push rail consumed by mobile TASK-009 and, later, the admin
communications surface.

> Note: the WEB-007 task file references "SCR-005", which is stale — SCR-005 is
> already `store_compliance` and SCRs are applied through SCR-009. This work
> ships as **SCR-010**, the next free number.

### New enum
- `notif_kind`: `MESSAGE`, `OFFER`, `BOOKING_REQUEST`, `LISTING_SOLD`,
  `ORDER_UPDATE`, `REVIEW`, `PAYOUT`, `SYSTEM` — values match the shipped mobile
  `api.ts` `NotifKind` union EXACTLY (do not rename; only `ADD VALUE` later).

### New tables
1. **`notifications`** — one row per in-app notification, owned by one user.
   Written by the server (service role / domain events); read by the owner.
   - `id uuid PK`
   - `user_id uuid not null references profiles(id) on delete cascade`
   - `kind public.notif_kind not null`
   - `title text not null`
   - `body text` (nullable)
   - `href text` (nullable)
   - `read_at timestamptz` (null = unread; source of truth)
   - `unread boolean generated always as (read_at is null) stored` — mirrors the
     mobile `ApiNotification.unread` field so the DB row maps 1:1
   - `created_at timestamptz not null default now()`
   - Index `(user_id, created_at desc)` for the feed; partial `(user_id) where
     read_at is null` for unread counts.

2. **`device_push_tokens`** — Expo push tokens per user device.
   - `id uuid PK`
   - `user_id uuid not null references profiles(id) on delete cascade`
   - `token text not null`
   - `platform text check (platform in ('ios','android','web'))`
   - `created_at` / `updated_at` (touch trigger) / `last_used_at timestamptz`
   - `unique (user_id, token)` — upsert-friendly register + dedupe.
   - Index on `(user_id)` and `(token)`.

### RLS policies
- `notifications`: `SELECT` own rows only; `UPDATE` own rows only (mark read,
  ownership preserved). No `INSERT`/`DELETE` for authenticated — the server
  inserts from domain events via the service role.
- `device_push_tokens`: a user fully manages ONLY their own rows
  (`SELECT`/`INSERT`/`UPDATE`/`DELETE` scoped to `auth.uid()`). Service role
  prunes dead tokens.

### Realtime
- `notifications` added to the `supabase_realtime` publication so mobile gets a
  live in-app feed. RLS still applies over Realtime, so a client only receives
  its own rows.

### Edge Function (deployed)
- `notifications-dispatch` — POST-only, service-role-authenticated. Stores one
  in-app notification per recipient (always), then fans out Expo push to each
  recipient's `device_push_tokens`, chunked at the Expo 100-message limit, and
  prunes tokens reported as `DeviceNotRegistered`. Uses a server-only
  `EXPO_ACCESS_TOKEN` Edge secret; returns 503 when it is unconfigured.

## Why

Mobile TASK-009 needs a notification store (in-app feed via Realtime) plus
server-side push. The dispatch function centralises fan-out so any domain event
(new message / offer / order update) is one service-to-server call, and dead
Expo tokens are pruned automatically on `DeviceNotRegistered`. The in-app row is
stored before push is attempted, so notifications are never lost when a device
has no token or has denied push permission.

## RLS intent

- `notifications`: a user reads and marks-read ONLY their own notifications;
  they can never insert notifications for another user (server-only writes).
- `device_push_tokens`: a user registers/updates/removes ONLY their own device
  tokens; the service role additionally prunes globally-dead tokens.

## Rollback / compatibility

Additive changes only. New tables are empty on migration; the new enum is not
referenced by any existing table. Safe to migrate forward; rollback would drop
the two tables and the `notif_kind` enum, and remove `notifications` from the
Realtime publication.

## Secrets

- `EXPO_ACCESS_TOKEN` — server-only Expo access token for the push send API.
  Edge secret ONLY; never `NEXT_PUBLIC_*` / `EXPO_PUBLIC_*`.
