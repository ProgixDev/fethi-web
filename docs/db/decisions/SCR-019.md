# SCR-019 — `seller_fee_receivables` (deferred handoff-sale platform fee)

Status: Accepted
Date: 2026-08-21
Author: Dev (mobile issue #36, no-card handoff purchases)
Reviewed-by: chaine100informatique@gmail.com (explicit sign-off in-session,
2026-08-21 — approved the deferred-receivable design in ADR-0003 and this
schema before the migration was applied)
Migration: supabase/migrations/20260821120000_scr019_seller_fee_receivables.sql

## What changes

One additive, forward-only change:

- **New enum `public.fee_receivable_status`**: `('OUTSTANDING', 'SETTLED', 'WAIVED')`.
- **New table `public.seller_fee_receivables`**:
  - `id uuid primary key default gen_random_uuid()`
  - `seller_id uuid not null references public.profiles(id) on delete cascade`
  - `order_id uuid not null references public.orders(id) on delete cascade`
  - `reason text not null` — free-text tag, e.g. `'handoff_no_card'`. Deliberately
    `text`, not an enum, matching SCR-018's `rate_limit_hits.scope` precedent: a
    future reason (a disputed refund shortfall, a promo clawback) shouldn't need
    its own migration to add an enum value.
  - `amount_cents integer not null check (amount_cents > 0)`
  - `status public.fee_receivable_status not null default 'OUTSTANDING'`
  - `settled_at timestamptz` — null until settled/waived.
  - `settled_via text` — free-text reference to whatever cleared it (a Stripe
    payout id, an admin note for a manual waive). Populated by #35's settlement
    logic, not by anything in this SCR.
  - `created_at timestamptz not null default now()`
  - `updated_at timestamptz not null default now()`, maintained by the existing
    `touch_updated_at()` trigger (SCR-003 precedent).
  - `constraint seller_fee_receivables_one_per_order unique (order_id)` — v1
    scope is exactly one receivable per handoff order; also gives the
    idempotent `orders-create` call a natural no-op-on-replay guarantee.
- **Index** `seller_fee_receivables_seller_outstanding_idx` on `(seller_id)
  where status = 'OUTSTANDING'` — the query #35's settlement logic will run at
  payout time ("what does this seller currently owe").
- RLS enabled: sellers can `select` their own rows (all statuses, so a future
  "pending deductions" screen can show history, not just the open balance).
  No `insert`/`update`/`delete` policy for `authenticated`/`anon` — service-role
  only writer, same pattern as `orders`/`offers`/`idempotency_keys`.

No existing table, column, enum, or policy is touched.

## Why

ADR-0003 (`docs/adr/0003-defer-handoff-fee-to-seller-receivable.md`) is the
business rationale: issue #36's no-card handoff path moves no money through
the platform, so #30's buyer-protection fee can't be collected at order time
the way it is for card sales (deducted from the Stripe Connect transfer). A
$0 fee on handoff was rejected — it would let every `VENTE` transaction dodge
the platform's only revenue line by choosing handoff over card. This SCR is
the technical design for the chosen alternative: record what's owed now,
collect it out of that seller's first real Connect payout once #35 ships.

**Explicitly out of scope here**: the settlement side (deducting outstanding
receivables at payout time) is #35's work, not this SCR's. This SCR only adds
the ledger table and the write path that records the debt. Until #35 ships,
rows accumulate as `OUTSTANDING` with nothing consuming them — see ADR-0003's
"Consequences" for why that's intentional, not an oversight.

## RLS intent

- `select`: `seller_id = auth.uid()`, `authenticated` role. A seller can read
  their own receivables (any status) — supports a future "pending platform
  fees" view without needing a new Edge Function just to read this table.
- No `insert`/`update`/`delete` policy for `authenticated` or `anon`. The
  table has exactly one writer: `orders-create`'s service-role client (this
  SCR); a future settlement job (#35) will be the only other writer, also
  service-role.
- Buyers have no visibility into this table (it's seller-side proceeds
  accounting, not buyer-facing) — no policy needed since the default is deny.

## Edge Function (if any)

Extends the already-deployed `orders-create` (no new function). Its existing
`paymentMethod === 'handoff'` branch (built for issue #36) gains one more
step, inside the same idempotent block as the order insert and the
thread/system-message write:

```ts
if (paymentMethod === 'handoff') {
  // pricing.amountCents: listing price for a direct handoff, or the agreed
  // offer amount if this handoff settles an accepted offer.
  const feeCents = Math.round(pricing.amountCents * HANDOFF_RECEIVABLE_FEE_RATE); // 0.05, matches mobile fees.ts
  if (feeCents > 0) {
    await svc.from('seller_fee_receivables').insert({
      seller_id: listing.owner_id,
      order_id: order.id,
      reason: 'handoff_no_card',
      amount_cents: feeCents,
    });
  }
}
```

Idempotency: relies on `idempotentReplay` already wrapping the whole handler
(a retried request replays the cached response and never re-runs this
insert) *and* the `seller_fee_receivables_one_per_order` unique constraint as
a second line of defense against any non-retry double-call.

No new secrets, no new auth path — reuses `orders-create`'s existing
service-role client.

## Affected consumers

- Mobile: fethi-mobile issue #36 — the write path above is required for the
  handoff purchase flow to actually record what it owes the platform;
  without it, `ADR-0003`'s decision has no implementation. No mobile UI
  reads this table yet (a "pending platform fees" seller view is plausible
  future work, not required for #36's acceptance criteria).
- Web: none today. `docs/features/admin/orders_disputes_finance_flow.md`
  (existing admin finance surface) is a natural future home for an
  "outstanding receivables" view — not built by this SCR.
- Future: fethi-mobile issue #35 (checkout/Connect payout work) will need to
  read `seller_fee_receivables` (filtered `status = 'OUTSTANDING'` by
  `seller_id`) at payout time and write `status = 'SETTLED'` +
  `settled_at` + `settled_via`. Flagging this dependency now so #35's design
  doesn't reinvent the ledger shape.

## Rollback / compatibility

Purely additive — new table, new enum, no foreign keys pointing into it from
anywhere else. Safe to drop with zero blast radius if the deferred-receivable
model is abandoned in favor of one of ADR-0003's rejected alternatives —
nothing else references this table.

Applied and verified live 2026-08-21: `fethi-mobile/e2e/task-036-handoff-purchase.contract.mjs`,
22/22 assertions passing against the real deployed `orders-create` — order
creation (VENTE-only enforced, LOCATION rejected), thread + verbatim SYSTEM
message, the receivable row (amount/status/reason), RLS (seller reads own
row, buyer/outsider/direct-client-write all denied), and idempotent replay
not double-booking the message or the receivable.

## Notes

- Amounts are informational-turned-real: the 5% figure matches
  `SELLER_PROTECTION_FEE_RATE` in `fethi-mobile/src/shared/lib/fees.ts`
  exactly, computed server-side here for the same reason `orders-create`
  already recomputes card pricing server-side (WEB-016) rather than trusting
  the client.
- This table intentionally does **not** touch `orders.fee_cents` — that
  column reflects what's actually charged as part of the order (0 for a
  handoff order, since nothing is charged at order time); the receivable is
  a separate, later-collectible amount. Conflating the two would make
  `orders.fee_cents` mean different things for different payment methods.
