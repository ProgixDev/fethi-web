## What changes

Additive, forward-only. The staff/admin authorization model for the web admin app.

- Enum `staff_role` = admin | moderator | finance | support.
- Table `staff_members` — `user_id uuid PK references auth.users(id) on delete
  cascade`, `roles staff_role[] not null default '{}'`, timestamps. The **source
  of truth** for who is staff and what they may do.
- `SECURITY DEFINER` helpers `is_staff(uid)` and `has_staff_role(uid, role)` so
  later admin tables (WEB-009..014) can gate RLS on staff role.
- RLS: a staff member may `SELECT` **only their own** row; all writes are
  service-role only (the invite / role-management flow). No `anon` access.

## Why

WEB-004 protects `(admin)/(authed)` with Supabase Auth + role-based access. Authz
must never derive from user-editable `user_metadata`. A table checked **per
request** (not a JWT claim) means a role downgrade reflects on the very next
request — see the task's edge cases. Roles are an array to match the shipped
`roles: string[]` admin contract. Board: WEB-004; gates WEB-009..014.

## RLS intent

- `staff_members`: `SELECT` to `authenticated` where `(select auth.uid()) =
  user_id` (read own row only). No INSERT/UPDATE/DELETE policy → writes are
  service-role only. The server route guard reads the caller's own row via the
  session client; cross-user staff management uses the service-role client.
- Helper functions run `security definer set search_path = public` so RLS on
  other tables can ask "is this caller a moderator?" without exposing the table.

## Edge Function (if any)

None. (Staff invite / role edits are service-role route handlers in the admin app,
added with the admin-management UI; not part of this SCR.)

## Affected consumers

- Web: WEB-004 (this), and gates all admin UI tasks WEB-009..014 (the actor model
  for moderation / finance / disputes).
- Mobile: **none** — staff roles are web-only. The regenerated types still vendor
  to mobile (the table appears in the contract; mobile RLS exposes nothing).
