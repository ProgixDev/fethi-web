## What changed

Three additive, forward-only changes, all in one migration:

1. **`listings.publication_request_id uuid`** (nullable) + unique index
   `listings_owner_publication_request_id_key` on `(owner_id,
   publication_request_id) WHERE publication_request_id IS NOT NULL`. Lets the
   mobile publish screen keep a stable client-generated request id across a
   retried publish call: if the first response is lost after Postgres
   committed, the retry's `INSERT` hits the unique index (`23505`), and the
   client looks up the existing listing by `(owner_id,
   publication_request_id)` instead of creating a duplicate.
2. **`listing_photos_listing_storage_path_key`** — unique index on
   `listing_photos (listing_id, storage_path)`. Photo-sync can replay after a
   client timeout without duplicating a listing image; existing callers
   already identify an image by storage path, so this is purely a
   dedup/idempotency guard, not a new column.
3. **`listing_publication_notifications`** — a one-row-per-listing ledger
   (`listing_id primary key references listings(id) on delete cascade`,
   `notification_id references notifications(id) on delete cascade deferrable
   initially deferred`, `created_at`). RLS is **enabled with zero policies**
   (default-deny to every PostgREST role — `anon`, `authenticated`, and even
   the row's own owner). It exists purely as an auditable dedup key for the
   trigger below; nothing reads it through the API.
4. **`notify_listing_published()`** — a `SECURITY DEFINER` trigger function
   (`search_path = ''`, fully schema-qualified references) fired `AFTER INSERT
   OR UPDATE OF status ON listings`. It no-ops unless the row's new `status =
   'ACTIVE'` **and** the row is not already coming from an ACTIVE row (i.e. it
   fires on `DRAFT → ACTIVE` and on a fresh `INSERT ... status = 'ACTIVE'`, but
   never on an `ACTIVE → ACTIVE` update touching some other column). It inserts
   into the ledger with `ON CONFLICT (listing_id) DO NOTHING` inside a CTE, and
   only inserts the `notifications` row when that CTE actually produced a row —
   so the ledger's primary key is what makes the whole side effect
   exactly-once, including under a client retry that re-sends the same
   `UPDATE`/`INSERT`. `EXECUTE` on the function itself is revoked from
   `public, anon, authenticated` — it is only ever invoked by the trigger, not
   callable directly.

## Security / privacy

- **`listing_publication_notifications`**: RLS `ENABLE ROW LEVEL SECURITY`
  with **no policies at all**. Verified locally (see Evidence below) that
  `anon`, a non-owner `authenticated` user, and even the listing's own owner
  (`authenticated` as `owner_id`) are all denied both `SELECT` (0 rows) and
  `INSERT` (`42501 new row violates row-level security policy`) against this
  table through the PostgREST roles. Only the table owner (`postgres`, via the
  `SECURITY DEFINER` function, which runs as the function's owner and bypasses
  RLS for that owner) can write it. This table is intentionally invisible to
  the API — it is a server-side dedup ledger, not a consumer-facing resource.
- **`notifications`**: unchanged — the trigger inserts into the existing
  SCR-010 table (own-row RLS: the owner can `SELECT` their own row via the
  existing policy; nobody else can). Verified locally that a non-owner
  `authenticated` user sees 0 rows for the owner's publication notification,
  while the owner sees exactly 1.
  the trigger writes a `SYSTEM`-kind notification whose `body` interpolates
  the listing's own `title` (owner-authored, not otherwise sensitive) via
  `format()` — no injection risk (parameterized) and no cross-user data
  exposure (the `href` only ever points at the listing being published).
- **Trigger function**: `security definer` + `set search_path = ''` (every
  reference inside the function body is schema-qualified — `public.listings`,
  `public.notifications`, `public.listing_publication_notifications`) is the
  standard hardening for a `SECURITY DEFINER` function per
  `docs/db/CONTRACT.md` / Postgres/Supabase guidance, closing the
  search-path-hijack class of privilege-escalation bug. `EXECUTE` is revoked
  from `public, anon, authenticated` so it cannot be invoked directly — only
  the trigger mechanism calls it.
- **`listings.publication_request_id`**: nullable, client-supplied UUID with
  no semantic meaning beyond idempotency; the unique index is scoped to
  `(owner_id, ...)` so one seller cannot collide with (or discover) another
  seller's request id. No new read surface — it is a plain column covered by
  the existing `listings` RLS (owner read/write, public read only when
  `status = 'ACTIVE'`, unchanged by this migration).
- **`listing_photos` unique index**: no RLS/column change, purely a dedup
  constraint on data already reachable under the existing `listing_photos`
  policies.

## Evidence (live, local Supabase — `node_modules/.bin/supabase start`, all
migrations through this one applied, Postgres 17 in Docker)

Fixtures: one `auth.users` + `public.profiles` row (`id
11111111-1111-1111-1111-111111111111`, owner).

| Step | Action | Ledger rows | `notifications` rows |
| --- | --- | --- | --- |
| 1 | `INSERT listings ... status='DRAFT'` (id `2222…`) | 0 | 0 |
| 2 | `INSERT listings ... status='ACTIVE'` (id `3333…`, direct insert) | 1 | 1 |
| 3 | `UPDATE listings SET title=... WHERE id=3333…` (unrelated column) | 1 (unchanged) | 1 (unchanged) |
| 4 | `UPDATE listings SET status='ACTIVE' WHERE id=3333…` (no-op transition, already ACTIVE) | 1 (unchanged) | 1 (unchanged) |
| 5 | `UPDATE listings SET status='ACTIVE' WHERE id=2222…` (DRAFT → ACTIVE, first real publication) | 1 (new row for `2222…`) | 1 (new row for `2222…`) |
| 6 | Repeat step 5 (no-op ACTIVE→ACTIVE again) | 1 (unchanged) | 1 (unchanged) |

RLS (after granting base `SELECT/INSERT/UPDATE/DELETE` to `anon`/
`authenticated` to isolate RLS-policy behavior from grant-level denial — this
local CLI stack's default ACLs for objects owned by `postgres` do **not**
include base table grants for `anon`/`authenticated`, unlike the hosted
platform, so testing RLS specifically required granting the baseline first;
see Notes):

- `anon`: `SELECT` on ledger → 0 rows. `INSERT` on ledger → `42501 new row
  violates row-level security policy for table
  "listing_publication_notifications"`.
- `authenticated` as a **non-owner** user: `SELECT` on ledger → 0 rows;
  `SELECT` on `notifications` filtered to the owner's new row → 0 rows.
  `INSERT` on ledger → same `42501` RLS denial.
- `authenticated` as the **owner**: `SELECT` on `notifications` for their own
  new row → 1 row (existing SCR-010 own-row policy, unaffected by this
  migration). `SELECT` on ledger → 0 rows. `INSERT` on ledger → same `42501`
  RLS denial — confirms the ledger has **zero** policies, not just
  non-owner-scoped ones; nobody can write it through PostgREST, including the
  listing's own owner.

Full SQL + output is in the PR description / available on request; the
scripts used were ad hoc `psql` sessions against the local
`postgresql://postgres:postgres@127.0.0.1:54322/postgres` connection (docker
container `supabase_db_<project-ref>`).

## Notes

- The local Supabase CLI stack's default ACLs (for tables owned by role
  `postgres`, which is what `supabase start` runs migrations as) do **not**
  grant `anon`/`authenticated` base `SELECT`/`INSERT`/`UPDATE`/`DELETE` on
  `public` schema tables the way the hosted platform's project bootstrap does.
  This is a known local-stack/platform divergence, not something this
  migration changes — it only affected how the RLS evidence above had to be
  gathered (base grants had to be added locally first so that a `42501` could
  be attributed to an RLS policy rather than a missing table grant). It does
  not affect production behavior.
- No enum values changed, no column was renamed or dropped, no existing RLS
  policy was touched — this SCR is purely additive per `COORDINATION.md` §3.
- `listing_photos_listing_storage_path_key` matches the `onConflict:
  'listing_id,storage_path'` already used by the mobile PR's
  `syncListingPhotos` upsert (see fethi-mobile PR #40) — the index is what
  makes that upsert's conflict target valid.
