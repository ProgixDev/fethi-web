## What changes

Two additive, forward-only changes:

- **`profiles.kyc_session_id uuid`** (nullable) and **`profiles.kyc_decision
  jsonb`** (nullable). `profiles.kyc_status` (SCR-001, enum `UNVERIFIED |
  PENDING | VERIFIED | REJECTED`) stays the single field the app and admin
  dashboard read for status — these two are additive detail (which Didit
  session, and the full decision breakdown) for staff KYC review depth, not a
  second source of truth.
- **New table `didit_webhook_events`**: `event_id`, `session_id`,
  `webhook_type`, `status`, `signature_method`, `signature_valid boolean not
  null`, `raw_body text not null`, `processed boolean`, `error`,
  `created_at`. No unique constraint — see Why for why idempotency is a
  read-before-write check in the function instead. RLS enabled, no policies
  (service-role only, matches `idempotency_keys`/`rate_limit_hits`).

No existing table, column, or enum is touched — `kyc_status`'s 4 real values
are unchanged; Didit's richer status vocabulary maps onto them in the Edge
Function (see below), not by widening the enum.

## Why

Issue #28 needs a Didit webhook receiver. Two design calls worth recording:

1. **Idempotency table logs EVERY delivery attempt, not just successes** —
   the spec explicitly wants signature failures debuggable ("log the raw
   body for debugging signature failures") and "each delivery attempt is a
   new WebhookLog row." A plain `stripe-webhook`-style dedup-only table
   (claim event_id via a unique constraint, one row per event ever) can't
   support that — Didit's own retry policy redelivers the same event_id up
   to twice, and each of those redeliveries needs its own logged row. So
   idempotency here is a read-before-write check in the function (skip
   reprocessing if a prior `signature_valid + processed` row already exists
   for this `event_id`), not a DB uniqueness constraint — deliberately the
   opposite of `stripe-webhook`'s pattern, for this specific reason.
2. **`kyc_status` keeps its existing 4-value enum** rather than growing to
   match Didit's 9 statuses 1:1. Didit's `In Review`/`In Progress` both map
   to `PENDING`, `Not Started`/`Abandoned`/`Expired`/`KYC Expired` all map to
   `UNVERIFIED`, `Resubmitted` maps to `PENDING` — full detail is preserved
   in `kyc_decision`/the webhook log, not lost, just not promoted into the
   status enum. Keeps every existing consumer of `kyc_status` (the mobile
   `kyc-status` Edge Function, the admin KYC list) working unchanged.

## RLS intent

`didit_webhook_events`: service-role only, no `authenticated`/`anon` policy
— identical precedent to `idempotency_keys` (SCR-003) and `rate_limit_hits`
(SCR-018). Nothing client-side reads this table; it exists for the webhook's
own idempotency and for staff/ops debugging via the service role.

`profiles.kyc_session_id`/`kyc_decision`: no new policy needed — `profiles`
already has an owner-read policy (SCR-001) that covers these two columns
like any other profile column. The **mobile `kyc-status` Edge Function
already only reads `kyc_status`** (not these two new columns), so nothing
mobile-facing changes shape. A future admin KYC-detail view is the intended
reader of `kyc_decision`, not built by this SCR.

## Edge Function (if any)

New function **`didit-webhook`** (no user JWT — `--no-verify-jwt`, self-
verified via HMAC, same pattern as `stripe-webhook`/`revenuecat-webhook`).

- Reads the raw body as text FIRST (before any JSON parsing), per Didit's
  spec — needed for the raw-bytes `X-Signature` variant and to avoid
  re-encoding drift.
- Verifies `X-Timestamp` freshness (≤300s), then tries `X-Signature-V2`
  (sorted, Unicode-preserved canonical JSON HMAC — algorithm confirmed
  against Didit's own docs, not guessed), falls back to `X-Signature` (raw
  bytes HMAC — provably correct here since Deno's `req.text()` gives exact
  wire bytes, no re-encoding), falls back to `X-Signature-Simple` (envelope
  only) as a last resort. Constant-time comparison throughout.
- Logs every delivery (verified or not) to `didit_webhook_events`; claims
  `event_id` (idempotent — a duplicate delivery is a 200 no-op) only once
  actually verified.
- Maps `status` → `profiles.kyc_status` per the table above; on `Approved`,
  also writes `kyc_session_id`/`kyc_decision`.
- Secrets: `DIDIT_WEBHOOK_SECRET` (per-destination `secret_shared_key` from
  the Didit Business Console — **not yet set**, since the destination itself
  doesn't exist until the function is deployed and its URL is registered
  there). Returns 503 `didit_unconfigured` if missing, same pattern as
  `stripe-webhook`'s missing-secret guard.

Full behavior documented in the function's own file, not duplicated here.

## Affected consumers

- Mobile: fethi-mobile issue #28. The mobile `kyc-status` Edge Function
  (already deployed) reads `profiles.kyc_status`, which this webhook now
  keeps current — no mobile code change required for the webhook itself to
  take effect.
- Web: none yet. `kyc_decision`/`kyc_session_id` are staff-review material;
  no admin screen reads them today (the existing `/api/admin/kyc` list only
  reads `kyc_status` + `payout_accounts`). A KYC-detail view surfacing the
  decision breakdown is plausible future work, not required here.

## Rollback / compatibility

Purely additive. `didit_webhook_events` has no inbound references from
elsewhere — safe to drop with zero blast radius. The two new `profiles`
columns are nullable with no default logic depending on them; every existing
`profiles` reader is unaffected (`select *` call sites would see two new
null columns, not a behavior change — checked: no `select('*')` on profiles
exists in either repo, all reads are explicit column lists).
