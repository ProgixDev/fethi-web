# SCR-018 — `rate_limit_hits` (per-user rate limiting for the category-suggest Edge Function)

Status: Accepted
Date: 2026-08-20
Author: Dev (mobile issue #25 backend dependency, fethi-mobile branch `feat/issue-25-category-suggest`)
Reviewed-by: chaine100informatique@gmail.com (explicit sign-off in-session, 2026-08-20 — approved the
table design and the 5/user/day limit before this migration was applied)
Migration: supabase/migrations/20260820153449_scr018_rate_limit_hits.sql

## What changes

One additive, forward-only change:

- **New table `public.rate_limit_hits`**: `user_id uuid` (FK → `profiles.id`,
  cascade delete), `scope text`, `window_start timestamptz`, `hit_count
  integer default 0`, primary key `(user_id, scope, window_start)`.
- **Index** on `window_start` (for periodic cleanup of expired windows, not
  currently automated — see Notes).
- RLS enabled, **no policies added** — service-role only, same pattern as
  `idempotency_keys` (SCR-003).

No existing table, column, enum, or policy is touched.

## Why

Issue #25 ("Suggest a listing category from its photo with GPT-5 nano")
requires a server-side Edge Function that calls a paid third-party API
(OpenAI) on a per-user action. Its acceptance criteria explicitly require
calls to be "authenticated, rate-limited per user, observable." Nothing in
either repo currently implements per-user rate limiting — no table, no KV,
no shared helper exists. This SCR adds the minimum reusable primitive for
that: a generic fixed-window hit counter keyed by `(user_id, scope,
window_start)`, deliberately not named after this one feature so a future
Edge Function needing its own rate limit doesn't need its own SCR/table —
it just uses a new `scope` value against this same table.

The limit itself (5 calls/user/day) is a product decision, confirmed with
the user in-session rather than invented: generous enough that no real
seller hits it in normal use (most list a handful of items a day), tight
enough to bound cost on a per-call-billed model provider.

## RLS intent

Service-role only. No `anon`/`authenticated` policy is added — the table is
invisible to PostgREST for direct client reads/writes, exactly like
`idempotency_keys`. All access goes through the `listing-category-suggest`
Edge Function's service-role client, which is the only writer and reader.
There is no scenario where a client needs to read its own rate-limit state
directly (the Edge Function returns a `429 rate_limited` error when the
caller is over the limit, which is suffient signal client-side).

## Edge Function (if any)

`listing-category-suggest` (mobile issue #25) is the first and currently
only consumer. On each call: `requireUser(req)` to get `user.id`, compute
`window_start` = today truncated to UTC midnight, then
`upsert(..., onConflict: 'user_id,scope,window_start')` incrementing
`hit_count`, reading back the new count in the same round trip. If the
returned count exceeds 5, the function returns `429 rate_limited` before
calling OpenAI. Full function behavior (auth, category validation, OpenAI
call, error mapping) is documented in the function's own file, not
duplicated here — this SCR is scoped to the table.

## Affected consumers

- Mobile: fethi-mobile issue #25, branch `feat/issue-25-category-suggest` —
  the `listing-category-suggest` Edge Function needs this table to exist
  before it can enforce its rate limit; without it the function would need
  to either skip rate limiting (violates the issue's acceptance criteria) or
  fail hard (worse UX than a real limit).
- Web: none. No admin surface reads/writes `rate_limit_hits`.

## Rollback / compatibility

Purely additive — a new table with no foreign keys pointing into it from
anywhere else, and no existing code path reads or writes it yet. Safe to
drop in a later migration with zero blast radius if the rate-limiting
approach changes (e.g. if a KV-backed limiter replaces it later — nothing
else would need to change to accommodate that).

## Notes

- No automated cleanup of old `window_start` rows exists yet. At 5
  rows/user/day worst case this is a slow-growing table; a scheduled cleanup
  (`pg_cron` or a periodic Edge Function) deleting rows older than N days is
  a reasonable low-priority follow-up, not required for this feature to
  ship correctly.
- Deliberately generic (`scope` column) rather than named
  `category_suggest_rate_limit` — see "Why" above.

## Unblocks

- fethi-mobile issue #25 — lets the `listing-category-suggest` Edge Function
  enforce its per-user rate limit as required by the issue's acceptance
