# WEB-022 — Support inbox: `support_tickets` schema + admin panel

Status: Review
Priority: P1
Project: MyStreet Web (DB owner)
Milestone: 10-day production launch
Owner: Dev A

## Purpose

fethi-mobile issue #77 ("Feedback admin"): founder called the support inbox
priority — users have no in-app way to message support, and the admin
`communications/support` page is an honest `NotConnectedNotice` placeholder
(there is no `support_tickets` table). This was deliberately deferred in the
previous feedback batch (PR #24) as too large for a quick fix. This task ships
the real thing: schema + RLS + the admin inbox UI. A follow-up mobile task
(TASK-029, filed on the fethi-mobile board) ships the consumer screen.

## Scope

- **Schema (SCR-028):** `support_tickets` + append-only `support_ticket_messages`,
  RLS (owner + staff `support`/`admin`), a trigger keeping the parent ticket's
  `last_message*`/unread counters/`status` in sync on new messages, both tables
  on `supabase_realtime`.
- **Admin UI** at `src/app/(admin)/(authed)/communications/support/`, following
  the `reports` repository/route-handler pattern (service-role client behind
  `/api/admin/support/*`, gated by `gateStaff('support')` — consistent with the
  rest of admin, not raw client RLS calls):
  - Inbox list: open/in-progress tickets first, subject, requester, last
    message preview, relative time, unread badge. Filter by status.
  - Ticket detail: message thread (oldest → newest), reply composer, status
    control (Open / In progress / Resolved / Closed).
- No admin-side realtime subscription in this task: every other admin surface
  is fetch-on-navigation/service-role, and introducing a client-side
  publishable-key RLS read path just for this screen is scope creep for a P1.
  A "Refresh" affordance (revalidate on focus/interval, like the rest of
  admin) is enough; the schema still carries both tables on
  `supabase_realtime` because **mobile** needs it.
- Out of scope: file/photo attachments, canned replies, SLA timers, staff
  assignment/ownership, a dedicated resolution-note field (the final staff
  message serves that purpose), email notification on new ticket.

## Edge cases (resolved during grilling)

- **Multiple concurrent tickets per user:** allowed — no uniqueness
  constraint. A user may have more than one unrelated request open.
- **`unread_by_staff` on ticket creation:** ticket creation always inserts the
  first `USER` message in the same request, so the trigger sets
  `unread_by_staff = 1` naturally. The column default is `0` (fixed from an
  earlier `1`, which would have double-counted against the trigger).
- **Auto status transitions:** none beyond the existing reopen-on-user-reply
  trigger. A staff reply does not auto-flip `OPEN` → `IN_PROGRESS`; staff sets
  status explicitly.
- **Staff attribution:** `support_ticket_messages.sender_id` already
  identifies which staff member sent a reply — no extra column needed.
- **Users closing their own ticket:** out of scope for this task (mobile only
  reads/replies); recorded as an open product question below.

## Open product questions (default applied, flag for founder)

- Should a user be able to mark their own ticket resolved from the mobile app
  (self-service close)? Default applied: no — only staff change status.
  Tracked in `docs/next-meeting-questions.md`.
