# WEB-017 — Payment↔order reconciliation, Connect payouts & escrow capture

Status: Review
Priority: P1
Project: MyStreet Web
Milestone: post-launch hardening
Owner: Dev A
Schema: SCR likely (capture state / transfer records) — file when scoped

## Purpose
Resolve the three coupled payment-architecture gaps from the review (**A1/A2/A3**).
Today the money rail and the order rail run independently and no funds reach
sellers.

## Resolution (2026-07-12) — product decisions taken
- **A3 capture timing → IMMEDIATE capture** (kept current behavior; no
  manual-capture/escrow). No code change.
- **A2 payout readiness → BLOCK purchase until the seller's Connect account is
  ENABLED**, via **destination charges**. Implemented in `payments-create-intent`:
  requires an `ENABLED` + `payouts_enabled` `payout_accounts` row for the seller
  (else `409 seller_payout_not_ready`); the PaymentIntent uses
  `transfer_data.destination = seller` + `application_fee_amount = order.fee_cents`
  (5% + 0.95€ sale floor is the platform's cut; seller receives the rest).
- **A1 completion-gated-on-payment → implemented** in `orders-transition`: a
  Stripe order (`payment_intent_id` set) can't `confirm-pickup` until
  `payment_status = SUCCEEDED` (else `409 payment_not_completed`); cash/non-Stripe
  orders (no intent) are unaffected.
- Bugfix **SCR-013**: `confirm_order_pickup` enum cast (the SCR-012 RPC failed to
  actually complete a pickup until this).

**Verified live:** seller-not-ready → blocked; unpaid Stripe order → confirm
blocked; paid order → buyer confirm → HANDOFF_PENDING → seller confirm →
COMPLETED. Deployed to prod.

### Remaining follow-ups (not blocking)
- Refunds on destination charges must set `reverse_transfer: true` (WEB-013
  refund action) so the seller transfer is clawed back.
- Mobile: surface `seller_payout_not_ready` / `payment_not_completed` with a
  friendly message (currently a generic error).
- Optional later: manual-capture escrow (A3) if product revisits buyer protection.

## Findings to resolve

### A1 — order completion and payment can diverge
`orders-transition` moves an order to COMPLETED on in-person handoff confirmation
with **no reference to `payment_status`**, and `stripe-webhook` moves
`payment_status` with no reference to `status`. So an order can be COMPLETED while
unpaid, or a payment can succeed on a CANCELLED order with no refund.
- Gate `confirm-pickup → COMPLETED` on `payment_status ∈ {SUCCEEDED, NULL(cash)}`.
- On cancel-after-capture, enqueue a refund (or block cancel post-capture).

### A2 — Connect onboarded but sellers are never paid
`payments-create-intent` creates the PaymentIntent with **no `transfer_data`,
`application_fee_amount`, or `on_behalf_of`**, so funds sit in the platform account
and `orders.fee_cents` is never applied.
- Decide **destination charges** (`transfer_data.destination` = seller's Connect
  account + `application_fee_amount`) vs **separate transfers** on completion.
- Only pay out to sellers whose `payout_accounts.onboarding_status = 'ENABLED'`.

### A3 — auto-capture happens before handoff (no escrow)
Default automatic capture takes the money at purchase, before the buyer receives
goods — misaligned with the handoff order model.
- Use `capture_method: 'manual'` at intent creation and **capture in
  `orders-transition` on COMPLETED** (this also structurally fixes A1). Handle
  auth-expiry (7-day capture window) and cancellation → void the authorization.

## Acceptance Criteria
- [ ] An order cannot reach COMPLETED unless paid (or explicitly cash/NULL).
- [ ] Payment captured on completion (manual capture) or a clear rationale for
      immediate capture is documented.
- [ ] Seller receives funds via Connect minus the platform fee; only ENABLED
      accounts are paid.
- [ ] Cancel/expiry paths void or refund correctly; no captured-but-cancelled
      orders without a refund.
- [ ] Webhook remains source of truth; all Stripe calls idempotent.
