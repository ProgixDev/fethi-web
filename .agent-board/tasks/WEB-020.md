# WEB-020 — Finish the admin surfaces still rendering static markup

Status: Review
Priority: P3
Project: MyStreet Web (DB owner)
Milestone: 10-day production launch
Owner: Dev B

## Purpose
The admin app is broadly wired — only 3 of 90 pages still import `@/lib/fixtures`.
But a set of pages were built as visual shells and never had a backing task, so they
look functional to an operator while doing nothing. Ranked by how misleading they are:

| Page | State |
| --- | --- |
| `dashboard` | GMV chart + activity feed on `fixtures/metrics` + `fixtures/activity` — self-documented in the source as awaiting a backend |
| `users/[id]/layout` | imports the fixture `User` **type** only — cosmetic, lowest priority |
| `settings/feature-flags` | static; toggles persist nothing |
| `settings/webhooks` | static |
| `settings/api-keys` | static |
| `communications/announcements` | static |
| `communications/templates` | static |

A dashboard showing invented GMV to a stakeholder is the one that actually costs
something; the settings shells are ordinary unfinished work.

## Scope
- Back the dashboard's GMV trend and activity feed with real read models (WEB-014
  built analytics read models — extend rather than duplicate). Until then, label the
  charts as sample data in the UI so nobody quotes them.
- For each static settings/communications page: wire it, or mark it clearly as
  not-yet-functional, or remove it from the nav. Any of the three is fine; leaving a
  toggle that silently discards its value is not.
- Drop the fixture `User` type import in favour of the generated row type.

## Acceptance Criteria
- [x] No admin page presents fabricated numbers as live data. Dashboard GMV/signups now
  come from `analyticsApi.marketplace()`/`signupsTrend()` (real, WEB-014). The activity
  feed has no backing read model — rather than build a new cross-entity aggregation for
  a P3 task, it's visibly labeled "Exemple" (sample data) per the scope's own sanctioned
  fallback, so it can't be mistaken for live activity.
- [x] Every reachable control either works or is visibly disabled. All 5 static
  settings/communications shells (feature-flags, api-keys, webhooks, announcements,
  templates) now show a "not connected to a backend" notice with every control
  `disabled` — none silently discard input anymore.
- [ ] `@/lib/fixtures` is no longer imported by any file under `src/app/(admin)/`. **Not
  fully met — deliberately.** `dashboard/page.tsx` still imports `fixtures/activity` for
  the now-labeled sample activity feed (see above). Every other admin file that imported
  fixtures (`users/[id]/layout.tsx`, `UserHeader.tsx`, `ListingActions.tsx`,
  `DashboardGmvChart.tsx`) has been moved to real generated/API types. A human should
  ratify whether the labeled-sample fallback is acceptable to close this criterion, or
  whether a follow-up task should build the real activity read model.
- [x] `npm run build` passes. Verified on the merged branch (typecheck clean, lint clean
  on touched files — one `react-hooks/set-state-in-effect` error in
  `users/[id]/layout.tsx` confirmed pre-existing via diff against the base commit, not
  introduced here).

## Build notes
Built as two agents in parallel across disjoint files (dashboard/activity/fixture-type
cleanup vs. the five settings/communications shells), merged cleanly with no conflicts,
then verified together: `npm run typecheck`, `npm run lint` (touched files only),
`npm run build`, and `npm run test:e2e e2e/tasks/WEB-020-dashboard.spec.ts
e2e/tasks/WEB-020-shells.spec.ts` — **8 passed, 1 skipped**. The skip
(`GMV trend reflects the live marketplace analytics endpoint, not a static fixture`) is
a service-role Supabase client construction failing in this sandbox
(`@supabase/realtime-js` requires native WebSocket support Node 20 here lacks) — the
same pre-existing gap `e2e/tasks/WEB-014.spec.ts` hits; not introduced by this task.

Judgment calls made without a human grilling pass (the `/grill-with-docs` step could not
run — it's user-invocation-only and can't be called by an agent):
- Activity feed: labeled-sample rather than a new backend aggregation (see above).
- All 5 settings/communications shells: uniformly "disable + label" rather than wiring
  any of them, since none has a backing table and wiring any would need a new SCR —
  disproportionate for a P3 task. Nav entries were kept (not removed) as more honest/
  discoverable than hiding the capability.
- `users/[id]/layout.tsx` switched from `publicUsersApi.get()` (which hardcoded every
  user to `status: "active", kyc: "unverified"`) to the real `usersApi.get(id)` — a
  correctness fix beyond the literal type-import scope.
- `UserHeader.tsx` dropped the fabricated phone line and tab counts (Transactions,
  Signalements) rather than inventing substitutes; `neighborhoodName()` helper dropped
  in favour of `user.neighborhood` directly (it's a free-text column, not a slug needing
  a lookup).
- `ListingActions.tsx` is dead code (not imported anywhere, confirmed via grep) — fixed
  to typecheck against real fields rather than deleted, since removing unused-but-typed
  components wasn't in scope.
