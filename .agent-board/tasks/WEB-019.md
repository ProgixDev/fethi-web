# WEB-019 — SCR: `search_listings_nearby` RPC (use the PostGIS index we already built)

Status: Ready
Priority: P2
Project: MyStreet Web (DB owner)
Milestone: 10-day production launch
Owner: Dev A

## Purpose
SCR-001 created a generated `geography(Point, 4326)` column on `listings` and a GiST
index over it (`listings_location_gix`), per ADR-0001. **Nothing queries it.**
`st_dwithin` appears in no migration and no application query in either repo.

Because there is no proximity RPC, the mobile client approximates radius search with
a lat/lng bounding box and then filters to the exact radius **in JavaScript, after
pagination** — which corrupts result counts, breaks pagination, and makes
nearest-first ordering per-page rather than global (details in mobile TASK-022).
For a hyperlocal marketplace this is the core discovery query, so the approximation
is not a small compromise.

## Scope
- File an SCR for a `search_listings_nearby(...)` SQL function:
  - `st_dwithin(location, st_makepoint(lng, lat)::geography, radius_m)` for the
    filter, `st_distance(...)` for the ordering, `limit`/`offset` server-side,
    and an exact total count.
  - Carries the filters the client already composes: `listing_type`, `category_id`,
    `status`, `condition`, `neighborhood`, price range, and the text search over
    title/description.
  - Returns the same projection the mobile `LISTING_SELECT` expects, plus
    `distance_m`, so the client seam does not have to reshape rows.
- Security: the function must not leak exact `lat`/`lng` of listings the caller
  cannot already see. Prefer `security invoker` so existing RLS applies unchanged;
  if `security definer` is unavoidable, gate it explicitly and justify it in the SCR.
- Confirm via `EXPLAIN` that the GiST index is used and not sequentially scanned.
- Regenerate `src/lib/database.types.ts`, vendor into mobile, and write the
  `MOBILE-SYNC-NOTES.md` entry in the same PR (unblocks mobile TASK-022).

## Acceptance Criteria
