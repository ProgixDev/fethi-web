# WEB-023 — Pre-publish listing moderation gate (`PENDING_REVIEW`) — issues #68 + #69

Status: Review
Priority: P1
Project: MyStreet Web (DB owner)
Milestone: 10-day production launch
Owner: Dev A

## Purpose

fethi-mobile issue #68 ("Feedback admin"): founder asked "Are listings
validated in admin before being published? Is everything connected on the
admin side?" Research this session found the honest answer is **no** — the
mobile "sell" flow (`sell/review.tsx` → `listingsApi.create`) defaults new
listings straight to `status = 'ACTIVE'`, and RLS (`listings_select_active`)
makes `ACTIVE` immediately publicly visible. There is no gate at all today.
The existing admin "moderation queue" (WEB-010/WEB-011) is a reactive
takedown queue (DRAFT/PAUSED/ARCHIVED), not a pre-publish approval flow.

This task adds an actual gate: new listings land in a new `PENDING_REVIEW`
state, invisible to the public, and require explicit staff approval to
become `ACTIVE`.

## Scope

- **Schema (new SCR):** add `PENDING_REVIEW` to the `public.listing_status`
  enum (`ALTER TYPE ... ADD VALUE` — non-transactional, must be its own
  migration/transaction boundary, cannot run in the same migration file as
  anything that uses the new value in the same transaction). RLS already
  restricts public `select` to `status = 'ACTIVE'` only — no RLS policy
  change needed, `PENDING_REVIEW` is invisible to `anon`/`authenticated`
  public reads by construction; owners still see their own row via
  `listings_select_own`.
- **Notification on entering review:** a trigger (mirroring
  `notify_listing_published`) that notifies staff when a listing transitions
  into `PENDING_REVIEW`, reusing the existing staff notification plumbing
  (same mechanism the support inbox / reports flows use — do not build new
  infra).
- **Admin UI:** extend the existing moderation queue
  (`src/app/(admin)/(authed)/listings/moderation/page.tsx`,
  `ListingsRepository.moderationQueue()`) to surface `PENDING_REVIEW`
  listings as the primary "needs approval" set — distinguish from the
  existing DRAFT/PAUSED/ARCHIVED takedown items (separate section/tab, or a
  clear status badge/sort-to-top; implementer's call). Approve action calls
  the existing `ListingsRepository.setStatus` (`PENDING_REVIEW` → `ACTIVE`),
  which already has audit-log wiring via `gateStaff('moderator')`. A
  reject/request-changes action should also be available (`PENDING_REVIEW` →
  `ARCHIVED` or back to `DRAFT` — implementer's call, document the choice).
- **Mobile-side change is NOT built in this task** — this is fethi-web/admin
  only. Document the required mobile change (`sell/review.tsx` /
  `listingsApi.create` in `fethi-mobile/src/shared/lib/api.ts` must stop
  defaulting `status` to `ACTIVE`, default to `PENDING_REVIEW` instead; plus
  UI copy so the seller understands their listing is "under review, not yet
  live") in `docs/MOBILE-SYNC-NOTES.md` so the follow-up fethi-mobile task
  can pick it up directly. Until the mobile PR ships, this migration is
  dormant (no listings will actually reach `PENDING_REVIEW`) — that's
  expected and safe; it doesn't change behavior for existing/live traffic
  until mobile flips its default.
- Out of scope: bulk approve/reject, SLA/auto-expiry of pending listings,
  reviewer assignment, email (vs. in-app/push) notification, changing
  behavior of already-live `ACTIVE` listings (no backfill needed — nothing
  transitions retroactively).

## Edge cases (decided, not grilled further — proceed on these defaults)

- Editing/republishing an already-`ACTIVE` listing does **not** re-enter
  `PENDING_REVIEW`. Only first-time creation is gated. `listingsApi.create`
  called from `my-listings/[id]/edit.tsx` for "republish" keeps the caller's
  existing status; the gate only applies to genuinely new listing rows with
  no prior status.
- Owner-initiated pause/unpause (`PAUSED` → `ACTIVE`) does **not** re-enter
  `PENDING_REVIEW` — only first publish is gated, unpausing stays entirely
  owner-controlled.
- Recorded in `docs/next-meeting-questions.md` for founder awareness (not
  blocking): whether repeat offenders / previously-rejected sellers should
  eventually get stricter re-review rules — out of scope for this MVP gate.

## Addendum: issue #69 folded in (same PR)

fethi-mobile issue #69 ("Feedback admin") turned out to be the founder's
reaction to the exact pre-existing bugs this task fixes, plus one more: the
admin `/notifications` page (`src/app/(admin)/(authed)/notifications/page.tsx`)
had a hardcoded, non-interactive example row "Annonces en attente de
modération" with fake example text, never wired to real data — matching all
three of the founder's complaints (not clickable, confusingly labeled,
unclear purpose). Fixed in the same PR: that card is now sourced from the
live `PENDING_REVIEW` count (`listingsApi.moderationQueue`), only renders
when the count is > 0, and links to `/listings/pending`. The other three
example cards on that page (KYC/disputes/payouts) are untouched — out of
scope, still honestly labeled as illustrative.

      of `PENDING_REVIEW` listings, polled every 60s) replaces a DB

      notification rows to staff would reintroduce it. The badge reuses the

      `AdminSidebar`, consistent with the codebase's actual "staff
      notification" precedent (unread counters, not push).

      — a DB trigger blocking an owner from self-approving their own listing

      plus the existing `listingsApi.update()` client call would let a seller
      bypass the entire gate. Covered by e2e.
