# WEB-013 — Orders, disputes, finance, refunds

Status: Backlog
Priority: P1
Project: MyStreet Web
Milestone: 10-day production launch
Owner: Dev B
Schema: none (uses WEB-005 `orders` + WEB-006 payments; SCR-NNN only if `disputes`/`refund_requests` tables are needed)

## Purpose
Admin views for orders, disputes, finance reconciliation, and refunds — reading the orders/payments the shared backend owns, with staff-gated refund/dispute actions executed through Stripe.

## Scope
- Orders list + detail.
- Finance reconciliation read models: GMV, fees, payouts.
- Disputes queue.
- Refund action: Stripe refund via a service-role Edge Function / route handler, recorded locally; the Stripe webhook reconciles final state.
- All data access behind `src/lib/api.ts` (`ordersApi`/`financeApi`).
- If `disputes` / `refund_requests` tables don't already exist in WEB-005/WEB-006, file an SCR.

## Acceptance Criteria
- [ ] Orders list/detail render with status incl. REFUNDED/DISPUTED.
- [ ] Finance reconciliation shows GMV, fees, and payout figures.
- [ ] Disputes queue lists disputed orders.
- [ ] Refund action triggers an idempotent Stripe refund and records it; webhook remains source of truth for final status.
- [ ] Stripe access via service-role Edge Function/route only (no STRIPE_* keys client-side).
- [ ] `npm run typecheck` passes.
- [ ] No new `npm run lint` errors in touched files.

## Technical Notes
- Routes/UI under `src/app/(admin)/(authed)/{orders,disputes,finance,refunds}`.
- Consumes `ordersApi` and `financeApi` in `src/lib/api.ts`; `OrderStatus` includes REFUNDED/DISPUTED. Note `ordersApi.list` is V1-shimmed over `/me/orders` — replace with `/admin/orders` once available; `financeApi.summary` currently aggregates client-side.
- Stripe refunds must be idempotent (idempotency key); webhook = source of truth for reconciliation.
- Read `node_modules/next/dist/docs/` before writing any route/handler code.

## Edge Cases
- Partial refund.
- Refund requested after payout already sent to seller.
- Dispute lifecycle (open → under review → won/lost) reconciliation.
- Double refund — idempotency must prevent it.
- Reconciliation mismatch between local records and Stripe webhook state.
